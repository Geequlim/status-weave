# Status Weave 执行路线图

本文把产品与开发计划拆成 Codex Agent 可以连续执行、持续验证的实施顺序。路线图不按工作日排期，而按“当前批次完成并通过验收后，立即进入下一批次”推进。

目标是尽快产生面板上可见的真实效果，同时保住 Cinnamon 主线程稳定性、共享采样和长期可维护性。

## 总体策略

采用“纵向切片优先、风险优先、逐项扩展”的开发方式：

1. 先稳定 TypeScript → Cinnamon CJS → 安装 → Looking Glass 验证链路。
2. 用 CPU 和内存完成第一条从系统采样到面板展示的完整闭环。
3. 尽早实现有序槽位和右键编排，验证产品最重要的差异点。
4. 形成稳定模板后，再依次扩展网络、hwmon、NVIDIA 和 AMD Provider。
5. 指标覆盖基本完成后，再补高级设置、性能回归和公开发布材料。

每个阶段结束时都必须有可安装、可观察的 applet；不接受长期只有底层接口而面板不可用的开发状态。

## Codex Agent 执行方式

- 每次选择最小但完整的纵向切片，连续实现、测试、构建、安装和读日志。
- 不用时间估算代替进度，只用通过或未通过的验收条件判断是否进入下一批。
- 纯解析器、数据模型和测试可以并行推进；Cinnamon 入口、共享服务和安装验证保持串行，避免互相覆盖。
- 遇到运行时错误时优先读取 Looking Glass 和 `journalctl`，修复后使用同一路径复验。
- 不为未来 Provider 提前设计复杂抽象；第二个真实用例出现后再提炼公共接口。
- 每一批都保持 applet 可安装、可回退，不积累大批未验证代码。

## 第一轮可见成果

第一轮执行不再继续扩写框架，直接把占位文本升级为可日用的最小状态条：

```text
CPU 18%  ·  RAM 7.4 / 31.1 GB
```

这一轮同时完成：

- 异步读取 `/proc/stat` 和 `/proc/meminfo`。
- 固定频率刷新面板文本。
- CPU 和内存纯解析测试。
- 两个实例共享同一份采样结果。
- 移除实例后停止其订阅；最后一个实例移除后停止采样。
- 构建、安装、Cinnamon 模块加载和 Looking Glass 日志验收。

只要这一轮通过，产品就已经从占位 applet 变成可实际使用的系统状态监控条。下一轮立即加入有序槽位和右键移动，不先扩展更多指标。

## 固定质量门禁

每个可安装变更都执行同一套验收：

```text
yarn tiny check
→ 构建 Spices 包
→ 使用 Cinnamon requireModule 验证入口
→ 安装开发版
→ 在面板添加或重载
→ 检查 Looking Glass / journalctl 日志
→ 验证移除实例后的资源释放
```

应尽快把 Cinnamon `requireModule` 检查和 Looking Glass 日志筛选固化为 Tiny 指令，减少重复人工排查。

## 执行批次 A：可靠的最小 applet

### 工作内容

- 保证占位 applet 能稳定添加、移除、重载。
- 添加两个实例，显示不同实例编号。
- 接入最小实例设置，并验证实例之间互不影响。
- 建立 applet 生命周期资源容器，统一登记和释放 timer、signal、subscription 与 subprocess。
- 增加 Cinnamon 入口集成检查和 Looking Glass 日志检查指令。

### 验收

- 连续添加、移除、重载十次无新错误日志。
- 两个实例同时存在且标识不同。
- 移除实例后没有残留 timer、signal 或订阅。
- 构建失败不会覆盖已安装的可用版本。

## 执行批次 B：CPU / 内存纵向闭环

### 工作内容

- 定义最小的 `Provider`、`Snapshot`、`Metric` 和 `Subscription` 接口。
- 将文件读取和时间来源放入 platform 适配层，业务解析保持纯函数。
- 实现 `/proc/stat` CPU 总利用率采样。
- 实现 `/proc/meminfo` 内存已用量、总量和使用率采样。
- 建立进程内共享 Telemetry Service；两个实例订阅同一指标时只采样一次。
- 在面板显示真实的 CPU 与内存值，并提供基础工具提示。
- 为 `/proc` 输入保存测试夹具，使用 Vitest 测试解析和两次采样差值。

### 验收

- 面板能持续显示真实 CPU 和内存数据。
- 两个实例不会让 Provider 采样次数翻倍。
- 非法或缺失输入只让相关指标不可用，不影响 applet。
- Cinnamon 主线程上不存在同步文件读取。

## 执行批次 C：有序布局与右键编排

这是 Status Weave 相比 Vitals 最重要的产品差异，应在指标大量扩展前完成。

### 工作内容

- 定义实例级有序槽位模型，包含指标、分隔符和分组槽位。
- 为槽位使用稳定 ID；显示、隐藏和重新启用不改变原始位置。
- 将槽位配置持久化到 Cinnamon 实例设置。
- 在右键菜单中实现：
  - 显示或隐藏指标。
  - 向左移动、向右移动。
  - 添加或移除分隔符。
  - 重置当前实例布局。
- 配置修改立即更新当前实例，不重新初始化共享 Provider。
- 测试排序、边界移动、隐藏恢复和配置迁移。

### 验收

- 用户不需要摘掉前面的指标就能调整顺序。
- 两个实例可以保存不同布局。
- 隐藏后重新显示的指标回到原有位置。
- 排序不会增加采样次数或重建 Telemetry Service。

## 执行批次 D：视觉系统与左键详情

状态：已完成。后续 Provider 复用本批次建立的状态、单位格式、稳定宽度、工具提示和独立详情页接口。

### 工作内容

- 建立统一的指标格式化器：百分比、温度、字节、速率和 RPM。
- 实现紧凑、标准、详细三种面板格式。
- 控制数值宽度和间距，减少刷新抖动。
- 加入正常、警告、危险和不可用状态。
- 左键打开只读详情面板，按类别展示所有已发现指标。
- 工具提示显示完整名称、来源设备、单位、状态和不可用原因。
- 提供默认隐藏的虚拟状态指标，使用同一表现链路验证正常、警告、危险、不可用和等待状态。
- 显式声明只支持 Cinnamon 水平面板。
- 视觉样式尽量继承 Cinnamon 主题，仅为状态添加必要强调。

### 验收

- 面板在连续数值刷新时没有明显宽度跳动。
- 左键只负责查看，右键只负责当前实例编排。
- 缺失指标有清晰但不打扰用户的退化状态。
- 顶部和底部水平面板可用；Cinnamon 能识别 applet 不支持垂直面板。

## 执行批次 E：逐个扩展 Provider

Provider 按当前使用价值排序开发，每个 Provider 独立达到验收后再开始下一个。

### E1：hwmon 温度与风扇

- 发现 `/sys/class/hwmon` 设备。
- 解析名称、标签、温度和风扇转速。
- 建立稳定设备 ID，避免重启或枚举顺序变化导致配置错位。
- 已完成面板格式、主题图标、按需采集及独立详情页。

### E2：网络

- 读取接口字节计数并计算上传、下载速率。
- 排除 loopback，处理接口新增、消失和计数器重置。
- 支持按接口显示和聚合显示。

### E3：NVIDIA

- 一次异步查询返回利用率、温度、显存和可用性。
- 使用固定 argv，不经过 shell。
- 加入超时、失败退避和严格输出解析。
- 已完成按需采集、面板格式、主题图标、休眠退化及独立详情页。

### E4：AMD / 集显

- 优先使用公开、可验证的 DRM/sysfs 接口。
- 对硬件和驱动差异保持明确的“尽力探测”边界。
- 无可靠数据时标为不可用，不估算或伪造。

### 每个 Provider 的统一验收

- 有真实录制夹具和纯解析测试。
- 无对应硬件时 applet 仍正常工作。
- Provider 失败不会中断其他指标。
- 多字段来自一次设备采样，不重复访问硬件。
- 真实机器数值与系统工具对照合理。

## 执行批次 F：预设与高级设置

### 工作内容

- 提供“概览”“GPU / 风扇”“网络”实例预设。
- 完成单位、精度、阈值、颜色和刷新偏好设置。
- 将实例设置与真正的全局 Provider 设置分开。
- 为旧配置增加版本号和最小迁移机制。
- 提供诊断信息：Provider 状态、最后成功时间、最近错误和退避状态。

### 验收

- 应用预设不会影响其他实例。
- 设置变更即时生效，不需要重启 Cinnamon。
- 配置升级不会无声丢失用户布局。

## 执行批次 G：稳定性与性能封板

### 工作内容

- 长时间运行并记录 CPU、内存、采样次数和日志量。
- 测试多实例、睡眠唤醒、网络变化、显卡模式切换和传感器消失。
- 审计所有同步 I/O、timer、signal、subscription 和 subprocess 生命周期。
- 检查失败退避，避免驱动异常时刷日志或高频重试。
- 在首批声明支持的 Cinnamon / Linux Mint 版本上回归。

### 验收

- 8 小时运行无持续增长的资源占用。
- 单个 Provider 连续失败时面板仍可操作。
- Looking Glass 没有持续错误或警告刷屏。
- 多实例不会按实例数线性增加硬件查询频率。

## 执行批次 H：公开发布

### 工作内容

- 补齐许可证、README、截图、支持矩阵和故障排查。
- 明确 NVIDIA、lm-sensors、内核接口和硬件支持边界。
- 生成干净的 Spices 发布包，不包含开发依赖、测试夹具和本机路径。
- 使用官方验证工具检查包结构。
- 建立版本号、变更日志和发布检查清单。
- 准备 Cinnamon Spices Pull Request。

### 验收

- 新用户可以按文档完成安装和配置。
- 发布包可从干净工作区复现。
- 隐私和安全边界清晰：不上传数据、不要求 root、不执行用户输入的 shell。

## 连续交付节点

### Alpha 1：可日用最小版

包含 CPU、内存、共享采样、有序布局、右键排序和多实例。达到验收后立即交付，不等待其他指标。

### Alpha 2：主要通用指标

增加网络、温度、风扇、左键详情和视觉状态。每个 Provider 独立完成、独立验证，不捆绑成一次大提交。

### Beta：混合显卡笔记本可用

增加 NVIDIA、AMD / 集显、预设和高级设置。优先在当前真实硬件上完成闭环，再扩大兼容范围。

### 1.0：公开发布

完成稳定性、兼容性、文档和 Spices 验证。达到发布门禁即发布，不设置人为等待周期。

## 当前下一步

当前项目已具备工程骨架、Tiny 指令、开发安装、占位 applet 和 Cinnamon 模块加载验证。Codex 接下来按以下队列连续执行：

1. 把 Cinnamon 入口验证和 Looking Glass 日志检查固化为 Tiny 指令。
2. 直接实现 CPU / 内存异步采样、共享刷新和面板显示。
3. 安装到当前 Cinnamon 会话并读取日志，修复到面板稳定显示。
4. 实现有序槽位与右键显示、隐藏、向左和向右移动。
5. 完成多实例持久化和生命周期验收。
6. 再进入网络、hwmon 和 GPU Provider，不在前面插入非关键功能。

队列中的每一步都由 Codex 持续执行到验收通过；只有涉及产品取舍、危险操作或无法从环境判断的硬件语义时才需要用户决策。
